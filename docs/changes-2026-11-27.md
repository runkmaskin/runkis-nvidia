### Descriptor tables per draw (offline)

Measured in game on 8d8db49 (`VICTORY_DRAW_PARTS=1`): 8,314 draws and dispatches a frame at 25.45 us a call, of which
tables 16.05 us. The list-thread profile put `HostHeap::make_listed` at 14.4 % (in it `make_twinned` 6.3 % and
`keep_ref` 6.1 %) and `draw::readable` at 8.6 %. What made tables expensive:
- **Views made again for every piece of a recording.** A list thread keeps the views a recording's tables copy
  (`ListViews`), but only for the last recording it translated. Threads take a recording a piece at a time (1,024
  words, some tens of draws) and then whichever recording has words, so nearly every piece threw the views away and
  made each again: `view_at`, `shadow::find`, `buffer_srv`, the driver's view creation.
- **Mirrored tables read through at every draw.** Tables without a constant buffer are not made afresh but mirrored
  (`table_entry`), and `readable` ran for every entry of every draw. Fresh tables already left a view read at the
  same list epoch alone (`Listed::ready`); these had no such rule.
- **SipHash and one lock on every texture read.** `upload_from` asked a global `Mutex<HashSet>` (SipHash) whether
  the host wrote the texture, then the list's texture set; `ensure_state` and `twin_use` asked the list's state and
  twin maps, all SipHash.

Changes:
- **`VICTORY_TABLE_CACHE=1`** (off by default, not run in game). (a) A list keeps its own views for its recording
  (`ListViews::of_list`, heaps of 1,024 slots made as views come, up to 8,192), so a view is made once a recording
  whichever thread takes the piece; only one thread translates a recording at a time. They are let go when the
  list's tables are (`tables_done`). (b) A mirrored entry's shader resource view read at the list's present epoch
  with the same tested depth target is left as read, the rule fresh tables have (with `VICTORY_READY_ONCE`).
  Off: the old code, byte for byte.
- Same results, no switch: `HOST_WRITTEN` is a shared lock over FxHash (`host_wrote` for `upload_from` too); the
  list's texture states, twins and textures brought up to date are FxHash, and so are the tables of title memory by
  address (`memory.rs`). Only the prelude walks the state and twin maps, for barriers and copies of different
  textures, whose order SipHash made new each run anyway.
- `VICTORY_DRAW_PARTS=1` keeps its line and adds one: `tables per frame (VICTORY_TABLE_CACHE=0|1): views made N,
  copied N, recordings begun anew on a thread N; mirrored entries read N, left as read N`.

Tests: `descriptor::host::table_cache_tests` (interleaved recordings through a thread's views, the list's own and
each recording alone on its own thread, with views released and made again: the list's own always equal the
recording alone, slot bytes and held resources included; with nothing released all three agree; heaps grow),
`descriptor::tests::mirrored_entries_left_as_read_change_nothing` (two heaps and lists alike, records rewritten,
epochs moved and title writes between draws: the same steps, refreshed ranges, textures and held resources after
every draw; it fails if the epoch is left out of the rule), `texture::host_written_tests`. Release benchmarks,
*offline* (`cargo test --release -p victory-gpu --lib -- --ignored --nocapture table_cache`):

| Benchmark | Before | After |
|---|---|---|
| 8,314 draws of a 30-view fresh table, 60 lists in pieces of 20 draws on 8 threads | 8.2 us a draw, 5.9 views made | 5.6 us a draw, 0.9 made |
| Mirrored table of 12 buffer views, 20,000 draws, one thread | 1.5-1.8 us a draw | 0.5-0.7 us a draw |
| `HOST_WRITTEN`, 100,000 asks on 8 threads | 11.2 ms | 2.5 ms |

What to read in game with `VICTORY_DRAW_PARTS=1`: the `tables` part (16.05 us at 8d8db49) with and without
`VICTORY_TABLE_CACHE=1`, and the new line: `views made` should fall to about once per view a list names, and
`left as read` should take most of `read`. Risks: a list's views live until its tables are let go, not until the
thread's next recording (more descriptor heaps, about 32 KiB a list for each 512 views, and the views' resources
held a little longer); a view a recording copies is not made again in the same recording if what it shows changed
in between (a buffer's host copy replaced, a texture's first level shown), which was already so within one piece.
# Changes of 2026-11-27: audit fixes, memory work, launcher

None of this has been run against the title (it was not on the machine). Everything below was checked with the
workspace's tests, new tests written for each fix, offline micro-benchmarks and a real start of `victory.exe`.
Figures marked *offline* are not in-game gains; the last section lists what needs a game run.

## Shader translator (victory-shader, victory-gpu pipeline)

- **`s_min_*` / `s_max_*` set SCC to "result != 0".** RDNA2 sets it when S0 is chosen. Wrong for equal operands
  and for a chosen zero; any `s_cselect` / `s_cbranch_scc` after it went the wrong way. (`emit/lower.rs`)
- **`s_lshl{1..4}_add_u32` set SCC to "result != 0"** instead of the carry out of the 64-bit `(S0 << N) + S1`,
  which address arithmetic feeds into `s_addc_u32`. (`emit/lower.rs`)
- **A translator panic killed a pipeline worker.** The pipeline then stayed "being made" forever, and every later
  pipeline with the same shader killed another worker until none were left. A panic is now a failed translation
  (logged once, nothing cached), and the worker loop always gives its counts back. (`shader_cache.rs`,
  `pipeline.rs`, `pipeline/make.rs`)

Tests: `scalar_min_and_max_set_scc_when_the_first_operand_is_chosen`, `scalar_shift_and_add_sets_scc_to_the_carry_out`
(run on the GPU), `a_translator_panic_is_a_failure_and_stores_nothing`. The translator changed, so the shader cache
is rebuilt on the first start.

## Console memory and DirectStorage (victory-hle)

- **`XMemMapPhysicalPages` unmapped the target range before checking the page numbers**: one unknown page destroyed
  the existing mapping while the call reported failure. All pages are now checked first.
- **Physical page numbers were never reused.** The title keeps them in 21 bits; after ~120 GiB of allocations in a
  session they no longer fit. A free list (first fit, neighbours joined) now hands freed numbers out again.
- **`VICTORY_POOL_DISCARD`** counted its delay from a page's *first* unmapping, not its last, and could reset a page
  while a DirectStorage write into it was under way (losing the bytes). Each page now has its last-unmapped time,
  a page written since is never discarded, and writes hold a lock the discard waits for (only with the feature on).
- **DirectStorage allocated and zero-filled new buffers for every compressed request**; each worker now reuses
  growing scratch buffers (requests over 4 MiB still get their own).

## GPU translation (victory-gpu)

- **Heap-pass cache leak**: the per-heap ranges kept host copies of released heaps alive forever (never freed by
  `let_go_idle`), and a new heap at a released heap's address inherited its state. Heaps now have serial numbers;
  their entry goes with the heap.
- **Dynamic descriptor slots could be released into a newer heap at the same address**, handing out slots other
  lists still used. Release now checks the heap's serial.
- **`Shadow::writing` was quadratic and allocated per pending range.** *Offline* benchmark, 7,000 declares into one
  174 MB copy: 434 ms → 8.9 ms (release).
- **Heap-mirror pages that could not be read were dropped** until the title wrote them again; they are re-queued.
  `HostHeap::mirror` read title memory in place where the page could be gone; it now reads through the safe copy.

## Memory (RAM / VRAM)

- **Command allocators** were taken last-in-first-out, so over time every list held memory for the frame's
  largest recording. Lists are now matched to recordings by size class. *Offline*, real D3D12 lists, 96 lists × 20
  frames: private bytes grew 95–107 MB instead of 216 MB.
- **Shader cache on disk** grew forever (every translator change orphaned all entries; `.tmp-*` files were never
  removed). Entries now live in `shaders/gen-<translator>`. At start, dead temp files are swept, and so are other
  generations no run has used for 30 days (each run marks its own). The layout from before generations is never
  removed: older builds sharing `%LOCALAPPDATA%\victory` still read it.
- **Host pipeline library** (1.3–1.5 GB) only ever grew. A library of an older translator of these generations is
  opened beside a new one; what a run loads is carried over without a recompile, the rest goes at the next save.
  A library an older build saved (no generation file beside it) is kept whole and added to, never cut down.
- **Staging / texture pool blocks** were only freed inside a later allocation; they now settle once a second by
  the existing rule.
- **Hot-path allocations**: barrier and render-target calls build on the stack. *Offline*: 82 → 19 ns per call of
  4 barriers.
- **New log line every 5 s**: `memory by subsystem: private=… list_allocators=… windows=… gpu_used=…` (MB, each with
  a `_peak`), to see which part holds the memory.

### Shader translation speed (byte-identical DXIL)

Translating one shader takes 30–40 % less CPU time. Speedups:
- FxHash in the optimiser, bitcode and lowering tables;
- `Bools::given` walks its diagram instead of building throwaway nodes (structuring about 40 % faster);
- decode uses a dword table instead of a BTreeMap;
- each instruction's fields and effects are computed once;
- liveness walks set bits only;
- `Shader::op` remembers its declarations.

*Offline*, synthetic programs (benchmark in `emit/speed_tests.rs`):

| Program | Before | After |
|---|---|---|
| Large, 6,044 instructions | 34.5 ms | 22.0 ms |
| Huge, 15,044 instructions | 108.6 ms | 65.4 ms |
| Throughput on 16 threads | 1,010 shaders/s | 1,588 shaders/s |

The DXIL bytes are identical on all 16 programs. `victory shaders` now runs one worker pool over all files; before, a file holding one shader was translated on one thread.

### The submitting thread's hot spots from the in-game profile (offline)

A WPR profile on commit 886ae0e (5500X3D, a 3060-class card, ~4,600 draws a frame, 69 ms a frame) had
`victory-submit` busy 57 % of a core. Exact-result changes, each with an equivalence test against the old code
on fixed seeds and a micro-benchmark (`cargo test --release -p victory-gpu --lib -- --nocapture <name>`):
- **Copies in the card's memory** (`carded.rs`, `shadow::card_dirty`): the register was walked whole at every
  submission (`vec::retain::closure<Weak<Shadow>>`, 3.6 %). A copy now tells the register when its flag first
  goes up, and the submission visits only those, in the register's order; the dead are swept when it has doubled.
  `send_copied` upgrades only the copies a title buffer copy reaches. 1,000 copies: 12 us a taking -> 0.03 us
  with none touched, 0.7 us with 8, 2.7 us with 64. Tests `carded::tests` (also changes from four threads
  beside the taking: none lost, none twice).
- **Tables grown per submission** (`reserve_rehash`, 1.4 %): `stale_under_flights`' table is kept per thread
  and several refreshes of a copy on end are looked up once (20,000 refreshes of 4,500 copies: 170 -> 118 us);
  a submission's `Batch` is kept emptied with its room (`KeptBatch`); FxHash (`fx.rs`, a copy of the
  translator's) for tables that are only looked up. The two tables whose order reaches what is done (the
  ask-once spans, `written_spans`) keep their hasher and are made as before. Tests `host::under_tests`.
- **Copies in place** are taken out of a flush's refreshes before the threads get them (they copied nothing and
  said so first), after the asking they are part of.

### Present-time upscale to the window (off by default)

The title outputs 1080p on Series S. The swap chain had the texture's size and Windows stretched it to a larger
window bilinearly, which is blurry on a 1440p screen. New switch, off: **`VICTORY_PRESENT_SCALE=1`**
(`crates/victory-gpu/src/upscale.rs`). The swap chain then follows the window's client size (read with
`GetClientRect` at each present; a change goes through the existing `ResizeBuffers` path after `settle_now`; a
minimised window keeps the last size). One full-screen triangle draws the presented frame (after the interface
plane is laid over it) into the back buffer through a render-target view: each of the 4x4 source taps gets a
light contrast-adaptive sharpen against its four neighbours, then a Catmull-Rom resample held inside its nearest
2x2 texels, so edges do not ring. The aspect is kept, with black bars. The shader is our own, compiled with
`D3DCompile` at the first present like `compose.rs`. **`VICTORY_PRESENT_SHARPEN=<0..1>`** (default 0.3; 0: no
sharpen). sRGB textures are read and written through sRGB views; 10-bit and 16-bit float pass through; integer and
signed formats keep the old copy (and the texture-size swap chain). Where the window has the texture's size the
old `CopyResource` is used. Captures, probes and the frame recorder still read the title's texture; the panel is
drawn at the back buffer's size. Off: the old path, unchanged.

Tests: `upscale::tests::gpu_scaling_keeps_flat_areas_the_mean_and_black_bars` (64x36 to 128x72, 100x56, 128x96,
200x72 and 64x36, sharpen 0, 0.3 and 1: flat areas exactly flat, mean within 1.5 of 255, bars black, the same size
unsharpened gives the texels back), `the_swap_chain_follows_the_window_only_when_scaling` (a window of the texture's
size takes the copy), `the_frame_keeps_its_aspect_with_bars`, `sharpness_reads_both_decimal_marks`,
`only_formats_with_a_meaning_to_filter_are_scaled`. Cost, by timestamps (`gpu_scaling_cost_1080p_to_1440p`,

### The structure builder on 32-lane hosts (offline)

All 52 programs of the ray-tracing structure builder (`XboxBvhBuilder.dll`) now translate with host pipelines on
a 32-lane host (RTX 4070 SUPER, `VICTORY_HOST_WAVE=32`). Before, 49 did. The other 3 are block-wide prefix sums.
Each console wave adds the totals of the waves before it in a loop. That loop runs a different number of rounds in
each console wave, so its two host waves cannot meet there. Its `v_readfirstlane` of the running sum was refused
with "a first-lane read where not every lane runs".

That sum is made of scalars and LDS reads at scalar addresses, after the last LDS write. So every lane that is
there holds the same value, and each host wave's own first lane gives the console's value. The new
`first_lane_alike` (`emit/lower.rs`) proves this. It needs an instruction without a guard, lane by lane, of scalars
and such values, or an LDS read at such an address. That LDS read must come after a group barrier on every path
from the entry, and no LDS write may be reachable from that barrier. Every loop around the value's instruction must
also be around the read, and joins never count. It is used only where the lowering refused before. A translation
of the whole game (`translate --list`, 25,982 programs, host wave 32) gives the same DXIL hash for every other
program. So there is no switch. Tests: `wave64_tests::a_block_prefix_sum_over_console_waves_runs_in_waves_of_32`
(256 and 512 threads, exact against the CPU on the card; refused before the fix);
`a_first_lane_read_of_a_lane_value_in_a_loop_per_console_wave_is_refused` and
`a_first_lane_read_of_lds_that_may_still_change_is_refused` (still refused).

Not covered: 3 programs of `amd_fidelityfx_upscaler_xbox.dll` (one console wave a group) fail with "a lane mask
exchanged where not every lane runs". Their outer loop depends on `thread id - v_mbcnt`, which is the same in every
lane of a console wave. The lane-branch analysis does not know that. Fixing it would change `all_lane_blocks`
for every program, so it would need its own switch.

### The layer's memory: what the figures hold, and dead texture copies (offline)

What the `memory by subsystem` figures of a 6-minute run on a Ryzen 7 7800X3D / RTX 4070 SUPER / 31 GB PC hold
(measured in game, 2026-11-27: `private=26091 host_textures=6366 texture_blocks=5952 windows=3204
gpu_used=9068 gpu_shared_used=6739`; the run's own copystat line: 15,738 MB of it in memory, 1,704 MB free, 1,388 MB
left to commit):
- **`private` is the commit charge** (`PagefileUsage`), and the card's memory counts in it.
  `zerocopy::tests::what_counts_as_private` (offline, this PC) makes a 1 GiB default heap of textures, one of buffers,
  an upload heap and a 1 GiB committed texture: each adds 1,026-1,030 MB to it. About 15.8 GB of the 26 GB were the
  card's allocations (`gpu_used` + `gpu_shared_used`), not the PC's RAM in use.
- **`host_textures` and `texture_blocks` overlap.** `host_textures` is the size of every host texture alive,
  `texture_blocks` the 64 MiB heaps that the textures the title fills are cut from. A texture in a block counts in
  both. The card's memory for textures is the blocks plus `host_textures` less `texture_blocks_held` (new field):
  about 7 GB there, not 12. These are card memory. They cost no RAM unless Windows moves them out, but they do count
  in the commit charge. There is no CPU copy of a texture beyond its staging buffer (`texture_staging`, 48 MB),
  which `texture::let_go_idle` already lets go.
- **Of those, 2,312 MB were host copies of placed textures whose title memory was no longer mapped** (copystat
  estimate, no slot showing them). The title had given them up. The sweep keeps an idle copy for ten minutes while
  the card is under 88 % of its budget, and the run was at 86 %. Freed pieces are cut again for new textures, so
  holding these copies is what made the blocks grow.
- `gpu_shared_used` is the card's allocations in the PC's memory. Most of it is ours: windows of title memory
  (3,124 MB), staging blocks, list scratch, the system-memory side of buffer copies. That is RAM in use, and the next
  place to look after this.

## Landed private blocks held by their copy (VICTORY_LAND_HELD=1|2, off)

What the copy-back's bytes are for, read from the code and the 7800X3D log of 2026-11-27 (measured in game): of 756
pieces landed a frame, 441 go into private (write-watched) title memory at the title's own address, 315 into views
beside the guards. For views the copy a landing went through is already told it holds them (`VICTORY_LAND_TAKEN`,
318 of 319 blocks). For private memory nothing could tell the landing's writes from the title's, so the next refresh
read every landed page back and compared it: "landings in title memory looked at by refreshes per frame: 18.3 MB held
already and left, 0.1 MB the title's too". That is the census's "our other threads first 98.8 %": our refreshes
reading back what the card wrote, on the submitting thread's side of the frame.

New switch, off: **`VICTORY_LAND_HELD`** (`shadow::land_held`, `Shadow::landed_blocks`, `Shadow::hold_blocks`,
`watch::ask_blocks`, `host::relay_hold_landed`). The relay asks the kernel about the landed blocks (one asking per run
of blocks, whatever copies they are of), notes the answer in the journal as any asking is noted, then compares the
parts written since each copy took the block with its CPU side. A block that holds title memory's bytes is noted
taken as of that asking; the title's later writes have later numbers and are taken as before. Only parts the refresh
would have compared and left (whole 4 KiB pages a landing of this copy noted); their landing notes go as the refresh's
look would have taken them. `=1` does it before the landing's ranges are done with (no refresh comes first; the
title's fences wait for it), `=2` after the title is told and waiters are woken (a refresh that comes first reads its
blocks back as before). Title memory is only read: nothing the title reads changes. Other copies of the same memory
see the blocks written, as before.

Tests (`shadow::held_tests`): 48 fixed-seed runs of title writes (half of the same value), landings with title
writes after the bytes are in and between the asking and the look, partial and whole refreshes: after every refresh
title memory, the CPU side and the card side are byte for byte those of the old path (and some 100+ blocks held);
targeted: a held block is not read back, another copy takes the landed bytes, a title write after the asking is
taken, one before the look keeps the block unheld, a page no landing of the copy noted keeps it unheld; a title
thread writing all the while through 400 landings, looks (the test path and the relay's) and refreshes misses no
write. Each fails if the compare is left out.

Benchmark (offline, 7800X3D, `cargo test --release -p victory-gpu --lib -- --ignored --nocapture
bench_held_landings`; 448 blocks, ~6,700 pages written in 17 landings a frame): the refresh after the landings 0.99
ms (26.2 MB read back, on the wide pool) -> 0.03 ms; the landings' looks 0 -> 1.40 ms a frame on the relay and the
landing's threads, mostly the 17 kernel askings (~80-95 us each over a 28 MB range). So `=1` adds about that to the
fences' wait; `=2` keeps it off the fences, on the relay's idle time (16 ms a frame in the log).

In game, read the 5-s line `landed private blocks per frame (VICTORY_LAND_HELD=N): A looked at ..., B of them held
..., C held other bytes or could not be told; D MB compared, E kernel askings, F ms on the relay`, and against a run
with it off: "landings in title memory looked at by refreshes ... X MB held already and left" (should fall by about
B x 64 KiB), the frame line's `copies X ms` and "preparing", and with `=1` the relay's "landing in all". Known
difference from the old path, not seen by the tests: the old path's first refresh after a landing took the landing
notes of only the pages it covered; here all looked-at pages lose them at once. A page whose notes went this way and
that the title later rewrites with the same bytes is then sent up again (as for any page the title writes), where the
old path might have left it; that matters only where the card's side holds bytes no landing brought back.

Not done (the rest of "land on demand"): signalling fences before the landing with pages read-protected until they
are landed. Reasons in `docs/copy-back.md` section 3; in short, view memory's protections are the guards', a fault
handler that waits for a landing on a title thread can deadlock with our locks, the kernel fails system calls on
protected pages instead of faulting, and our own refreshes would fault on them.
