# Changes of 2026-11-27: audit fixes, memory work, launcher

None of this has been run against the title (it was not on the machine). Everything below was checked with the
workspace's tests, new tests written for each fix, offline micro-benchmarks and a real start of `victory.exe`.
Figures marked *offline* are not in-game gains; the last section lists what needs a game run.

## Fixed in the repository itself

| What | Before | Now |
|---|---|---|
| `PLAY.bat` in a source checkout | Set the cache and data folders inside the tree, which the layer refuses: the run stopped at start | Uses `%LOCALAPPDATA%\victory` when `.victory-root` is present; unpacked folders unchanged |
| `victory config` | Printed `POLICY VIOLATION` and exited 0 | Exits 1 when a path breaks the policy |
| `cargo test --workspace` | Did not compile (`HostShader` built without `half_views` in `emit/mod.rs`) | Compiles; every test passes |
| `cargo xtask policy` | Failed on `PLAY.bat` | Allows `.bat` and the launcher's C#/XAML sources (same size/magic/encoded-run checks) |
| `VICTORY_FRAME_LOG` | Flushed every 64 frames (3.5 s at 18 fps) | Flushed at most every 250 ms, so it can be read live |
| `play-nvidia.ps1` | Said the release build ignores the ray-tracing skip list (stale since 56be6f9) | Corrected; new `-PrintEnv` prints the settings as JSON and starts nothing |

## Shader translator (victory-shader, victory-gpu pipeline)

- **`s_min_*` / `s_max_*` set SCC to "result != 0".** RDNA2 sets it when S0 is chosen. Wrong for equal operands
  and for a chosen zero; any `s_cselect` / `s_cbranch_scc` after it went the wrong way. (`emit/lower.rs`)
- **`s_lshl{1..4}_add_u32` set SCC to "result != 0"** instead of the carry out of the 64-bit `(S0 << N) + S1`,
  which address arithmetic feeds into `s_addc_u32`. (`emit/lower.rs`)
- **A translator panic killed a pipeline worker.** The pipeline then stayed "being made" forever, and every later
  pipeline with the same shader killed another worker until none were left. A panic is now a failed translation
  (logged once, nothing cached), and the worker loop always gives its counts back. (`shader_cache.rs`,
  `pipeline.rs`, `pipeline/make.rs`)

Tests: `scalar_min_and_max_set_scc_when_the_first_operand_is_chosen`, `scalar_shift_and_add_sets_scc_to_the_carry_out`
(run on the GPU), `a_translator_panic_is_a_failure_and_stores_nothing`. The translator changed, so the shader cache
is rebuilt on the first start.

## Console memory and DirectStorage (victory-hle)

- **`XMemMapPhysicalPages` unmapped the target range before checking the page numbers**: one unknown page destroyed
  the existing mapping while the call reported failure. All pages are now checked first.
- **Physical page numbers were never reused.** The title keeps them in 21 bits; after ~120 GiB of allocations in a
  session they no longer fit. A free list (first fit, neighbours joined) now hands freed numbers out again.
- **`VICTORY_POOL_DISCARD`** counted its delay from a page's *first* unmapping, not its last, and could reset a page
  while a DirectStorage write into it was under way (losing the bytes). Each page now has its last-unmapped time,
  a page written since is never discarded, and writes hold a lock the discard waits for (only with the feature on).
- **DirectStorage allocated and zero-filled new buffers for every compressed request**; each worker now reuses
  growing scratch buffers (requests over 4 MiB still get their own).

## GPU translation (victory-gpu)

- **Heap-pass cache leak**: the per-heap ranges kept host copies of released heaps alive forever (never freed by
  `let_go_idle`), and a new heap at a released heap's address inherited its state. Heaps now have serial numbers;
  their entry goes with the heap.
- **Dynamic descriptor slots could be released into a newer heap at the same address**, handing out slots other
  lists still used. Release now checks the heap's serial.
- **`Shadow::writing` was quadratic and allocated per pending range.** *Offline* benchmark, 7,000 declares into one
  174 MB copy: 434 ms → 8.9 ms (release).
- **Heap-mirror pages that could not be read were dropped** until the title wrote them again; they are re-queued.
  `HostHeap::mirror` read title memory in place where the page could be gone; it now reads through the safe copy.

## Memory (RAM / VRAM)

- **Command allocators** were taken last-in-first-out, so over time every list held memory for the frame's
  largest recording. Lists are now matched to recordings by size class. *Offline*, real D3D12 lists, 96 lists × 20
  frames: private bytes grew 95–107 MB instead of 216 MB.
- **Shader cache on disk** grew forever (every translator change orphaned all entries; `.tmp-*` files were never
  removed). Entries now live in `shaders/gen-<translator>`. At start, dead temp files are swept, and so are other
  generations no run has used for 30 days (each run marks its own). The layout from before generations is never
  removed: older builds sharing `%LOCALAPPDATA%\victory` still read it.
- **Host pipeline library** (1.3–1.5 GB) only ever grew. A library of an older translator of these generations is
  opened beside a new one; what a run loads is carried over without a recompile, the rest goes at the next save.
  A library an older build saved (no generation file beside it) is kept whole and added to, never cut down.
- **Staging / texture pool blocks** were only freed inside a later allocation; they now settle once a second by
  the existing rule.
- **Hot-path allocations**: barrier and render-target calls build on the stack. *Offline*: 82 → 19 ns per call of
  4 barriers.
- **New log line every 5 s**: `memory by subsystem: private=… list_allocators=… windows=… gpu_used=…` (MB, each with
  a `_peak`), to see which part holds the memory.

## Later the same day

### Translator, second pass (GPU-run tests, each failing before its fix)

- **DPP16**: a source lane outside EXEC now follows `bound_ctrl` / `fi` as the ISA says. Before, the inactive lane's
  register was read.
- **DPP row masks** of a wave64 program run as two host waves of 32 now name the console's rows. Before, the upper
  half used the mask bits of rows 0 and 1.
- **64-bit scalar operands**: inline float constants (240–248) are the double's bits, as in `s_mov_b64 s[0:1], 1.0`.
- **`v_cmp_class_f32`** with `neg` / `abs` flips only the sign bit. Before, denormals and signalling NaNs were
  reclassified.
- **f32 division** (`v_div_scale` / `v_div_fixup`) follows the ISA's case order: `0/5`, `5/inf`, huge/0.5 and
  denormal quotients are right now.
- **Known, kept as they were**: a typed buffer store with an SOFFSET drops the offset, and `image_gather4_l` on a
  cube or array reads level 0. Refusing them would drop their pipelines' draws. Their tests are kept and ignored.

### CPU hot paths (equivalence tests; *offline* benchmarks)

| What | Before → after |
|---|---|
| Draw-table record lookup (tables over 64 records) | 130 µs → 11.7 µs (32 × 4,096) |
| Dynamic descriptor slots (u64 bitset) | 0.32 → 0.20 ms per simulated frame |
| `land_card` pieces | 1,437 µs → 82 µs (256 × 2,000) |
| Snapshot pool take + return | 4.0 → 0.7 µs |
| `changed_runs` (merging title bytes under shader writes, AVX2) | 45.8 → 11.1 ms (400 × 64 KiB, floats changed all over) |
| A pipeline finished during a library save | waited for the whole save → goes to its draws at once |
| Identical title pipelines | compiled per copy → made once and shared |

### Shader translation speed (byte-identical DXIL)

Translating one shader takes 30–40 % less CPU time. Speedups:
- FxHash in the optimiser, bitcode and lowering tables;
- `Bools::given` walks its diagram instead of building throwaway nodes (structuring about 40 % faster);
- decode uses a dword table instead of a BTreeMap;
- each instruction's fields and effects are computed once;
- liveness walks set bits only;
- `Shader::op` remembers its declarations.

*Offline*, synthetic programs (benchmark in `emit/speed_tests.rs`):

| Program | Before | After |
|---|---|---|
| Large, 6,044 instructions | 34.5 ms | 22.0 ms |
| Huge, 15,044 instructions | 108.6 ms | 65.4 ms |
| Throughput on 16 threads | 1,010 shaders/s | 1,588 shaders/s |

The DXIL bytes are identical on all 16 programs. `victory shaders` now runs one worker pool over all files; before, a file holding one shader was translated on one thread.

### Robustness (victory-hle)

- `XMemMapPhysicalPagesScatter` checks every page before unmapping anything.
- Delayed task-queue callbacks: one timer thread plus a small worker pool, instead of one OS thread each. A blocked
  callback holds up no other one, and the process no longer aborts when a thread cannot start.
- `WALLS_FILES`, `LOW_RESERVATIONS` and placeholder holes no longer grow forever.
- 32-bit `XMemAllocDefault` keeps alignments above 64 KiB.

### The submitting thread

[docs/submit-thread.md](submit-thread.md) maps the ~48 ms thread: what runs where, what waits on what, and the larger
options ranked by saving and risk. Two findings:

- The 6 ms "waiting for descriptor records" is a wait on the heap-sync thread, not work on the submitting thread.
- Port 2's fallback could put one slot into two parts of a round, on two threads: it was compared twice, its
  last-seen record was written by both, and it was counted as a false miss. That is fixed behind a switch, below.

### Launcher

- **Presets**: Standard, Max FPS, Sharp, Fewer glitches, Series X, Troubleshoot, and "Recommended for this PC",
  worked out from the card, CPU and RAM. Bigger PCs keep the measured video-memory set, because a larger
  render-target reserve and full-size textures had measured worse.
- **Warm up shaders**: translates every shader, then builds every recorded pipeline.
- **Benchmark page**: interleaved A/B runs with a warm-up and a measured window, optional scripted keys
  (`VICTORY_KEYS`), and a noise rule. Results are saved as JSON and exported as CSV.

### Recording and sending host GPU work

[docs/gpu-commands.md](gpu-commands.md): where a list call's time goes once it reaches host D3D12 (offline). The
driver's calls cost 4-20 ns each (a pipeline 60-120, a barrier 100-190), the thin stream and the draw state's lock
under 20 ns: the microseconds of a call are the layer's own work in `State::prepare` / `bind`. Added:

- `list/sets.rs`: redundant vertex/index buffer, root constant and root view sets left out (`VICTORY_SET_CACHE=1`,
  off). Model and GPU picture tests show identical state and pixels; 58 % fewer calls, about 10 ns a draw saved.
- `list/parts.rs`: `VICTORY_DRAW_PARTS=1` times each draw by part in a game run (measures only).
- `VICTORY_CALL_TIMES=0`: a diagnostics build stops timing every list call (55-70 ns a call).
- Benchmarks: `bench_redundant_sets`, `bench_submission_calls` (an `ExecuteCommandLists` with its signal is ~43 us),
  `bench_thin_call_floor`.

## First game measurement, and what changed after it

A friend's run (his build vs this fork, two runs each) found:
- **Better with this fork:**
  - cheaper per object drawn: 16.4/14.8 → 14.4/14.3 ms of frame per 1,000 objects;
  - shorter heap-pass wait: 6.9/5.1 → 2.4/3.7 ms;
  - shader translation 28 % faster: 217 → 156 s.
- **Worse with this fork:**
  - 1 % lows dropped: 6.8/5.7 → 4.9/4.5 fps;
  - more frames over 100 ms: 78/129 → 117/168.

Three changes had altered timing, not results, and went in on by default, against this project's own rule. They are now off by default, so those parts behave as before, and each can be switched on to measure it alone:
`VICTORY_POOL_SETTLE=1` (empty pool blocks freed once a second), `VICTORY_LIST_CLASSES=1` (idle lists taken by size class) and `VICTORY_SHARE_PIPELINES=1` (identical title pipelines share one pending pipeline).

## Frame pacing (see [frame-pacing.md](frame-pacing.md))

- **`VICTORY_FRAME_LOG` has six more columns** after the three it had: ms the title's thread spent in its present
  calls, ms it slept in frame waits, ms the presenter spent sending the back-buffer copy, ms in the swap chain's
  `Present` (and the latency wait), ms threads waited for pipelines, and the compiles (driver pipelines plus shader
  translations). Counting only; nothing waits differently. The launcher's `FrameStats.TryParse` reads the first
  three of 3 or more columns (a launcher built before this reads none of the new lines: rebuild it).
- **`VICTORY_PRESENT_LATENCY=1|2|3`** (off): a swap chain with a frame-latency object, waited for only while the
  frame is early. Off is the old swap chain. Not run in game.
- `frame.rs`: the tick logic is two pure functions now (`tick_after`, `passed_tick`), same results, with fake-clock
  tests: a late frame never sleeps, an early one sleeps to its tick, a 4 s hitch is not repaid with a burst.

## Threads and locks

See [threads-and-locks.md](threads-and-locks.md). The landing/records/views/under pools hand out their job
numbers by an atomic counter instead of a lock per job (same numbers, each once; tested against the old pool;
*offline* under 0.1 ms a frame). New switches, off by default: `VICTORY_POOL_PRIORITY=1` (the pools the
submitting thread and the relay wait for, above normal), `VICTORY_DSTORAGE_WORKERS=<n>`,
`VICTORY_DSTORAGE_WAKE_FEW=1` (not a win offline; for a streaming A/B). The dstorage debug line counts
`woken_idle`.

- Overlapping 4 MiB windows of title memory. Descriptor slots find windows by address alone, so this is risky
  without the game.
- A typed buffer store with an SOFFSET, and `image_gather4_l` on a cube or array (see the translator section).
- `GPU_RANGES` in `HostHeap::new` is never pruned.
- The larger submitting-thread options (card steps ahead, write watch ahead, two threads in a row) need the game to
  be done safely; see [submit-thread.md](submit-thread.md).

### Shared memory and zero-copy (offline)

[docs/shared-memory.md](shared-memory.md) maps how title memory reaches the card and benchmarks the ways on an
RTX 4070 SUPER with real D3D12 objects (`zerocopy.rs`, `bench_shared_memory`): today's copies, VRAM card sides,
UPLOAD/WC, GPU_UPLOAD (ReBAR) and heaps opened on title memory (`OpenExistingHeapFromAddress`). Found: the card
does not cache an opened heap in its L2 (16 reads of 1 MiB: 573 us against 49), and opening costs 0.2-15 ms. No
new path was added: in place (`VICTORY_INPLACE=1`) and ReBAR windows (`VICTORY_WINDOWS_BAR_MB`) exist and need a
game A/B. A page taken whole into a two-sided copy now goes straight in (0.64 -> 0.31 ms per 16 MiB, offline);
`SentRuns::note_joined` allocates less. Equivalence tests for all three.

### Speed-set picture faults (offline)

[docs/speed-mode-bugs.md](speed-mode-bugs.md) says what `VICTORY_RELAY=2`, `VICTORY_CARD_STEPS=2` and
`VICTORY_TEXTURE_NO_WAIT=1` each give up, and adds two switches, both off, not run in game:
- **`VICTORY_CROSS_WAIT=1|2|count`**: a submission that refreshes a host copy over bytes a flight writes through
  another host copy (the skinning's whole-heap view against a draw's buffer inside the heap) waits for exactly the
  flights that write them. `count` only counts. Suspected cause of stretched and jumping bodies with card steps.
- **`VICTORY_TEXTURE_RECHECK=1`**: a texture read through the kernel across a change of mapping is read again at
  its next refresh instead of being trusted until its hash turn. Suspected cause of rainbow skin.
Tests: `host::cross_tests`, `texture::recheck_tests`.

### Recording threads: exact CPU fixes from the game profile (offline)

From a WPR profile on 886ae0e (about 4,600 draws a frame; the eight `victory-list-*` threads 31 % of the process).
No switch: results are the same. Release micro-benchmarks, per frame of 5,000 draws, *offline*
(`cargo test --release -p victory-gpu --lib -- --ignored --nocapture list_cpu`):
- **FxHash** (`fx.rs`, the same file as victory-shader's) for tables only looked up, never walked: the placed
  texture sizes (`Spans`), `placed_bytes_from`'s table, the root SRV/UAV slots. Word arrays are keys through
  `WordKey`, hashed two words at a time (a byte-wise step was 4 steps a word): `[u32; 14]` 6.1 -> 2.7 ms, root
  slots 0.41 -> 0.07 ms. `make_listed` looks a made view up once instead of twice: 5.5 -> 0.8 ms.
- **No COM reference per slot**: `HostHeap::keep_ref` clones the resource only if the slot did not hold it
  (1.85 -> 0.67 ms with the same resource). Command signatures are kept per thread as borrows for the run
  (they are never released): 0.42 -> 0.03 ms on 8 threads, and one shared lock less.
- **Retirement in batches**: what the slots of one `bind` let go of is retired under one take of the
  retirement lock, later never sooner (8 threads: 20.2 -> 8.6 ms).
- The table of textures the host writes (`resource::alias_of`, read for each shader read of a placed texture)
  is a read lock: 5.8 -> 2.2 ms on 8 threads.
Tests: `descriptor::host::list_cpu`, `draw::signature_tests`.

### Copying back (offline; see [copy-back.md](copy-back.md))

- What "copying back X ms Y MB" counts: with the relay, the `victory-relay` thread's time in a landing from its start
  until the flights' ranges are done with (fetch wait included); Y is bytes stored into title memory, not fetched.
- **`VICTORY_BACK_CENSUS=1`** (off, measurement only): one landed 4 KiB page in 16 of private memory gets a one-shot
  guard; the line says who touched landed bytes first (the title's CPU, our next landing, our other threads, nobody).
- **`VICTORY_LAND_SEGMENTS=1`** (off): the relay lands up to the first fence or bottom-of-pipe write behind its
  flights, tells it, then lands the rest. Tests: `relay_tests::landings_cut_at_tells_cut_where_the_card_could`,
  `relay_tests::no_tell_lets_a_stale_byte_be_read`.
- Same results, no switch: fetched-piece runs reuse one list per job; the merges without `VICTORY_LAND` keep a piece's
  "before" bytes in memory of the thread instead of a new allocation per piece.
