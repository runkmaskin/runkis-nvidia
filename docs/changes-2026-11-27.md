### Descriptor tables per draw (offline)

Measured in game on 8d8db49 (`VICTORY_DRAW_PARTS=1`): 8,314 draws and dispatches a frame at 25.45 us a call, of which
tables 16.05 us. The list-thread profile put `HostHeap::make_listed` at 14.4 % (in it `make_twinned` 6.3 % and
`keep_ref` 6.1 %) and `draw::readable` at 8.6 %. What made tables expensive:
- **Views made again for every piece of a recording.** A list thread keeps the views a recording's tables copy
  (`ListViews`), but only for the last recording it translated. Threads take a recording a piece at a time (1,024
  words, some tens of draws) and then whichever recording has words, so nearly every piece threw the views away and
  made each again: `view_at`, `shadow::find`, `buffer_srv`, the driver's view creation.
- **Mirrored tables read through at every draw.** Tables without a constant buffer are not made afresh but mirrored
  (`table_entry`), and `readable` ran for every entry of every draw. Fresh tables already left a view read at the
  same list epoch alone (`Listed::ready`); these had no such rule.
- **SipHash and one lock on every texture read.** `upload_from` asked a global `Mutex<HashSet>` (SipHash) whether
  the host wrote the texture, then the list's texture set; `ensure_state` and `twin_use` asked the list's state and
  twin maps, all SipHash.

Changes:
- **`VICTORY_TABLE_CACHE=1`** (off by default, not run in game). (a) A list keeps its own views for its recording
  (`ListViews::of_list`, heaps of 1,024 slots made as views come, up to 8,192), so a view is made once a recording
  whichever thread takes the piece; only one thread translates a recording at a time. They are let go when the
  list's tables are (`tables_done`). (b) A mirrored entry's shader resource view read at the list's present epoch
  with the same tested depth target is left as read, the rule fresh tables have (with `VICTORY_READY_ONCE`).
  Off: the old code, byte for byte.
- Same results, no switch: `HOST_WRITTEN` is a shared lock over FxHash (`host_wrote` for `upload_from` too); the
  list's texture states, twins and textures brought up to date are FxHash, and so are the tables of title memory by
  address (`memory.rs`). Only the prelude walks the state and twin maps, for barriers and copies of different
  textures, whose order SipHash made new each run anyway.
- `VICTORY_DRAW_PARTS=1` keeps its line and adds one: `tables per frame (VICTORY_TABLE_CACHE=0|1): views made N,
  copied N, recordings begun anew on a thread N; mirrored entries read N, left as read N`.

Tests: `descriptor::host::table_cache_tests` (interleaved recordings through a thread's views, the list's own and
each recording alone on its own thread, with views released and made again: the list's own always equal the
recording alone, slot bytes and held resources included; with nothing released all three agree; heaps grow),
`descriptor::tests::mirrored_entries_left_as_read_change_nothing` (two heaps and lists alike, records rewritten,
epochs moved and title writes between draws: the same steps, refreshed ranges, textures and held resources after
every draw; it fails if the epoch is left out of the rule), `texture::host_written_tests`. Release benchmarks,
*offline* (`cargo test --release -p victory-gpu --lib -- --ignored --nocapture table_cache`):

| Benchmark | Before | After |
|---|---|---|
| 8,314 draws of a 30-view fresh table, 60 lists in pieces of 20 draws on 8 threads | 8.2 us a draw, 5.9 views made | 5.6 us a draw, 0.9 made |
| Mirrored table of 12 buffer views, 20,000 draws, one thread | 1.5-1.8 us a draw | 0.5-0.7 us a draw |
| `HOST_WRITTEN`, 100,000 asks on 8 threads | 11.2 ms | 2.5 ms |

What to read in game with `VICTORY_DRAW_PARTS=1`: the `tables` part (16.05 us at 8d8db49) with and without
`VICTORY_TABLE_CACHE=1`, and the new line: `views made` should fall to about once per view a list names, and
`left as read` should take most of `read`. Risks: a list's views live until its tables are let go, not until the
thread's next recording (more descriptor heaps, about 32 KiB a list for each 512 views, and the views' resources
held a little longer); a view a recording copies is not made again in the same recording if what it shows changed
in between (a buffer's host copy replaced, a texture's first level shown), which was already so within one piece.
# Changes of 2026-11-27: audit fixes, memory work, launcher

None of this has been run against the title (it was not on the machine). Everything below was checked with the
workspace's tests, new tests written for each fix, offline micro-benchmarks and a real start of `victory.exe`.
Figures marked *offline* are not in-game gains; the last section lists what needs a game run.

## Shader translator (victory-shader, victory-gpu pipeline)

- **`s_min_*` / `s_max_*` set SCC to "result != 0".** RDNA2 sets it when S0 is chosen. Wrong for equal operands
  and for a chosen zero; any `s_cselect` / `s_cbranch_scc` after it went the wrong way. (`emit/lower.rs`)
- **`s_lshl{1..4}_add_u32` set SCC to "result != 0"** instead of the carry out of the 64-bit `(S0 << N) + S1`,
  which address arithmetic feeds into `s_addc_u32`. (`emit/lower.rs`)
- **A translator panic killed a pipeline worker.** The pipeline then stayed "being made" forever, and every later
  pipeline with the same shader killed another worker until none were left. A panic is now a failed translation
  (logged once, nothing cached), and the worker loop always gives its counts back. (`shader_cache.rs`,
  `pipeline.rs`, `pipeline/make.rs`)

Tests: `scalar_min_and_max_set_scc_when_the_first_operand_is_chosen`, `scalar_shift_and_add_sets_scc_to_the_carry_out`
(run on the GPU), `a_translator_panic_is_a_failure_and_stores_nothing`. The translator changed, so the shader cache
is rebuilt on the first start.

## Console memory and DirectStorage (victory-hle)

- **`XMemMapPhysicalPages` unmapped the target range before checking the page numbers**: one unknown page destroyed
  the existing mapping while the call reported failure. All pages are now checked first.
- **Physical page numbers were never reused.** The title keeps them in 21 bits; after ~120 GiB of allocations in a
  session they no longer fit. A free list (first fit, neighbours joined) now hands freed numbers out again.
- **`VICTORY_POOL_DISCARD`** counted its delay from a page's *first* unmapping, not its last, and could reset a page
  while a DirectStorage write into it was under way (losing the bytes). Each page now has its last-unmapped time,
  a page written since is never discarded, and writes hold a lock the discard waits for (only with the feature on).
- **DirectStorage allocated and zero-filled new buffers for every compressed request**; each worker now reuses
  growing scratch buffers (requests over 4 MiB still get their own).

## GPU translation (victory-gpu)

- **Heap-pass cache leak**: the per-heap ranges kept host copies of released heaps alive forever (never freed by
  `let_go_idle`), and a new heap at a released heap's address inherited its state. Heaps now have serial numbers;
  their entry goes with the heap.
- **Dynamic descriptor slots could be released into a newer heap at the same address**, handing out slots other
  lists still used. Release now checks the heap's serial.
- **`Shadow::writing` was quadratic and allocated per pending range.** *Offline* benchmark, 7,000 declares into one
  174 MB copy: 434 ms → 8.9 ms (release).
- **Heap-mirror pages that could not be read were dropped** until the title wrote them again; they are re-queued.
  `HostHeap::mirror` read title memory in place where the page could be gone; it now reads through the safe copy.

## Memory (RAM / VRAM)

- **Command allocators** were taken last-in-first-out, so over time every list held memory for the frame's
  largest recording. Lists are now matched to recordings by size class. *Offline*, real D3D12 lists, 96 lists × 20
  frames: private bytes grew 95–107 MB instead of 216 MB.
- **Shader cache on disk** grew forever (every translator change orphaned all entries; `.tmp-*` files were never
  removed). Entries now live in `shaders/gen-<translator>`. At start, dead temp files are swept, and so are other
  generations no run has used for 30 days (each run marks its own). The layout from before generations is never
  removed: older builds sharing `%LOCALAPPDATA%\victory` still read it.
- **Host pipeline library** (1.3–1.5 GB) only ever grew. A library of an older translator of these generations is
  opened beside a new one; what a run loads is carried over without a recompile, the rest goes at the next save.
  A library an older build saved (no generation file beside it) is kept whole and added to, never cut down.
- **Staging / texture pool blocks** were only freed inside a later allocation; they now settle once a second by
  the existing rule.
- **Hot-path allocations**: barrier and render-target calls build on the stack. *Offline*: 82 → 19 ns per call of
  4 barriers.
- **New log line every 5 s**: `memory by subsystem: private=… list_allocators=… windows=… gpu_used=…` (MB, each with
  a `_peak`), to see which part holds the memory.

### Shader translation speed (byte-identical DXIL)

Translating one shader takes 30–40 % less CPU time. Speedups:
- FxHash in the optimiser, bitcode and lowering tables;
- `Bools::given` walks its diagram instead of building throwaway nodes (structuring about 40 % faster);
- decode uses a dword table instead of a BTreeMap;
- each instruction's fields and effects are computed once;
- liveness walks set bits only;
- `Shader::op` remembers its declarations.

*Offline*, synthetic programs (benchmark in `emit/speed_tests.rs`):

| Program | Before | After |
|---|---|---|
| Large, 6,044 instructions | 34.5 ms | 22.0 ms |
| Huge, 15,044 instructions | 108.6 ms | 65.4 ms |
| Throughput on 16 threads | 1,010 shaders/s | 1,588 shaders/s |

The DXIL bytes are identical on all 16 programs. `victory shaders` now runs one worker pool over all files; before, a file holding one shader was translated on one thread.

### The submitting thread's hot spots from the in-game profile (offline)

A WPR profile on commit 886ae0e (5500X3D, a 3060-class card, ~4,600 draws a frame, 69 ms a frame) had
`victory-submit` busy 57 % of a core. Exact-result changes, each with an equivalence test against the old code
on fixed seeds and a micro-benchmark (`cargo test --release -p victory-gpu --lib -- --nocapture <name>`):
- **Copies in the card's memory** (`carded.rs`, `shadow::card_dirty`): the register was walked whole at every
  submission (`vec::retain::closure<Weak<Shadow>>`, 3.6 %). A copy now tells the register when its flag first
  goes up, and the submission visits only those, in the register's order; the dead are swept when it has doubled.
  `send_copied` upgrades only the copies a title buffer copy reaches. 1,000 copies: 12 us a taking -> 0.03 us
  with none touched, 0.7 us with 8, 2.7 us with 64. Tests `carded::tests` (also changes from four threads
  beside the taking: none lost, none twice).
- **Tables grown per submission** (`reserve_rehash`, 1.4 %): `stale_under_flights`' table is kept per thread
  and several refreshes of a copy on end are looked up once (20,000 refreshes of 4,500 copies: 170 -> 118 us);
  a submission's `Batch` is kept emptied with its room (`KeptBatch`); FxHash (`fx.rs`, a copy of the
  translator's) for tables that are only looked up. The two tables whose order reaches what is done (the
  ask-once spans, `written_spans`) keep their hasher and are made as before. Tests `host::under_tests`.
- **Copies in place** are taken out of a flush's refreshes before the threads get them (they copied nothing and
  said so first), after the asking they are part of.

### The structure builder on 32-lane hosts (offline)

All 52 programs of the ray-tracing structure builder (`XboxBvhBuilder.dll`) now translate with host pipelines on
a 32-lane host (RTX 4070 SUPER, `VICTORY_HOST_WAVE=32`). Before, 49 did. The other 3 are block-wide prefix sums.
Each console wave adds the totals of the waves before it in a loop. That loop runs a different number of rounds in
each console wave, so its two host waves cannot meet there. Its `v_readfirstlane` of the running sum was refused
with "a first-lane read where not every lane runs".

That sum is made of scalars and LDS reads at scalar addresses, after the last LDS write. So every lane that is
there holds the same value, and each host wave's own first lane gives the console's value. The new
`first_lane_alike` (`emit/lower.rs`) proves this. It needs an instruction without a guard, lane by lane, of scalars
and such values, or an LDS read at such an address. That LDS read must come after a group barrier on every path
from the entry, and no LDS write may be reachable from that barrier. Every loop around the value's instruction must
also be around the read, and joins never count. It is used only where the lowering refused before. A translation
of the whole game (`translate --list`, 25,982 programs, host wave 32) gives the same DXIL hash for every other
program. So there is no switch. Tests: `wave64_tests::a_block_prefix_sum_over_console_waves_runs_in_waves_of_32`
(256 and 512 threads, exact against the CPU on the card; refused before the fix);
`a_first_lane_read_of_a_lane_value_in_a_loop_per_console_wave_is_refused` and
`a_first_lane_read_of_lds_that_may_still_change_is_refused` (still refused).

Not covered: 3 programs of `amd_fidelityfx_upscaler_xbox.dll` (one console wave a group) fail with "a lane mask

## Landed private blocks held by their copy (VICTORY_LAND_HELD=1|2, off)

What the copy-back's bytes are for, read from the code and the 7800X3D log of 2026-11-27 (measured in game): of 756
pieces landed a frame, 441 go into private (write-watched) title memory at the title's own address, 315 into views
beside the guards. For views the copy a landing went through is already told it holds them (`VICTORY_LAND_TAKEN`,
318 of 319 blocks). For private memory nothing could tell the landing's writes from the title's, so the next refresh
read every landed page back and compared it: "landings in title memory looked at by refreshes per frame: 18.3 MB held
already and left, 0.1 MB the title's too". That is the census's "our other threads first 98.8 %": our refreshes
reading back what the card wrote, on the submitting thread's side of the frame.

New switch, off: **`VICTORY_LAND_HELD`** (`shadow::land_held`, `Shadow::landed_blocks`, `Shadow::hold_blocks`,
`watch::ask_blocks`, `host::relay_hold_landed`). The relay asks the kernel about the landed blocks (one asking per run

parts written since each copy took the block with its CPU side. A block that holds title memory's bytes is noted
taken as of that asking; the title's later writes have later numbers and are taken as before. Only parts the refresh
would have compared and left (whole 4 KiB pages a landing of this copy noted); their landing notes go as the refresh's
look would have taken them. `=1` does it before the landing's ranges are done with (no refresh comes first; the
title's fences wait for it), `=2` after the title is told and waiters are woken (a refresh that comes first reads its
blocks back as before). Title memory is only read: nothing the title reads changes. Other copies of the same memory
see the blocks written, as before.

writes after the bytes are in and between the asking and the look, partial and whole refreshes: after every refresh
title memory, the CPU side and the card side are byte for byte those of the old path (and some 100+ blocks held);
targeted: a held block is not read back, another copy takes the landed bytes, a title write after the asking is
taken, one before the look keeps the block unheld, a page no landing of the copy noted keeps it unheld; a title
thread writing all the while through 400 landings, looks (the test path and the relay's) and refreshes misses no

## Display settings: windowed, borderless, full screen, size, monitor (off by default)

New switches, all unset by default; unset, the window is made exactly as before (`lifecycle.rs` `fit`, `host.rs`
`make_window`). The code is `crates/victory-gpu/src/display.rs`; the title's own window is placed in
`crates/victory-hle/src/modules/lifecycle.rs` (`place`), the layer's fallback window in `host.rs`.

- **`VICTORY_WINDOW=windowed|borderless|fullscreen`.** `borderless` and `fullscreen` are the same: the title's
  window loses its frame (`WS_POPUP`) and covers the whole chosen monitor. There is no exclusive full screen.

- **`VICTORY_MONITOR=n`**: monitor n in `EnumDisplayMonitors` order, 1 for the first; unset or past the last one,
  the primary monitor.
- With any of the three set: **Alt+Enter** switches between a framed and a borderless window (our window
  procedure takes it before the title; DXGI's own Alt+Enter is turned off with `MakeWindowAssociation`, as it
  would try exclusive full screen), and the process is made **per-monitor DPI aware**, so a scaled monitor reports
  its real pixels and a borderless window is not stretched by Windows.
- An unreadable value is named in a warning and left out; the others still apply.
- The mouse camera (`VICTORY_MOUSE`) holds the cursor at the centre of the foreground window's rectangle, so it
  works the same in each mode.

## What the title's fences wait for behind the relay, and two ways to shorten it (offline)

Why: a WPR profile of a title thread on the 7800X3D (540p, ~35 ms frames, the card busy 1-4 ms of them) found it
spinning half its samples on a fence: it calls the fence's address method (vtable +0x60), then MONITORX/MWAITX and
SleepEx until the value reaches its target. In stage 2 a fence is set only after its flight's landing
(`late_signal`), so the title waits for the relay's landing: about 18.8 ms a frame, 7.2 of them the fetch wait, 7.7
the merge (docs/copy-back.md).

**The latency line (diagnostics builds, always on with the relay).** `host/tells.rs`: a thread (`victory-tell-watch`)
notes when the card reaches each value of the host's fence; the relay notes when each landing begins, when its fetch
(or the part a tell waits for) is in, when it is merged, and when each fence value and bottom-of-pipe write is told.
Fences note the first time the title asks them for their value or address after a set (`fence.rs`, one load per
call, a store the first time). Every frame-rate line:

```
the title is told per frame: S fence values and W bottom-of-pipe writes; A of the fences were asked for by the title
since their last set: card done to told X ms each (most M): card done to landing begun a, to the fetch in b, to
merged c, to told d; the title asked T ms before told; behind flight F of N in their landing; every tell: ...;
fences asked most: <address> n x  ms behind flight f, ...
```

a = the relay busy with an earlier landing (or the watch thread's wake), b = gather, send and fetch wait, c = merge of
card copies and of PC copies and ranges done, d = read-backs and the tells ahead of it. With in-flight copies b is 0.

**`VICTORY_MERGE_SPREAD=1`** (off). One fetch for the landing (in parts with `VICTORY_FETCH_PARTS`, cut where
segments end: `segment_parts`); the pieces go segment by segment (`segment_ends`, the cuts of `segment_end`); after a
segment's pieces are merged come its PC copies (what earlier segments did not look through: `ranges_minus`), its
ranges done with and its tells, then the next segment's merge. What only gives back (plans' lists, card steps' lists)
comes after the last tell. Same order argument as `VICTORY_LAND_SEGMENTS`, without its fetch per segment. Not with
`VICTORY_FETCH_CHECK`.

**`VICTORY_FETCH_IN_FLIGHT=1`** (off; `VICTORY_FETCH_IN_FLIGHT_MB`, 64). Design 1 of docs/copy-back.md section 3. A
pass behind the compare, in the flight's own compare list (`host/in_flight.rs`, `SNAP`): per piece, the compare's
flag; if set, a place in the flight's room of a ring in memory the PC reads (an atomic counter in card memory), noted
beside the compare's result, and the piece's 64 KiB copied there. The landing then merges from the ring: no list, no
fence, no wait. Rooms are given at record time from a ring in order and taken back at `card_done`, sized from what
the last flight of the same shape flagged (x2 + 8, at most an eighth of the ring); a full room or ring costs the old
fetch. A landing is merged from the ring only if every piece is there (never a mix, so merges keep the old order),
and not if an old fetch since may have brought a later flight's bytes of a piece (`Newer`, bounded by the flights
sent when that fetch was done): an older snapshot would put them back. The merge leaves out the title's bytes sent
after the flight's own sends (`sent_as`), as the copy-queue fetch does; the notes of sends are kept up to the landed
flights' sends only (`relay_fetched_to`). Not with `VICTORY_FETCH_CHECK` (a piece copied in its flight is not torn).

Tests: `relay_tests::spread_tells_never_let_a_stale_byte_be_read` (every line of up to 8 flights and tells, 9 card
paces, the card running on between segments; merges store only what differs from the CPU side: at every tell every
flight ahead is in title memory, same tells and memory as the old landing), `a_landing_is_cut_into_segment_ends`,
`segment_parts_keep_to_their_segments` and `ranges_minus_is_the_plain_difference` (fixed seeds),
`copies_inside_the_flight_never_let_a_stale_byte_be_read` (every line of up to 8 things, 48 fixed-seed schedules
with the card running on until the old fetch and a flight under way caught by it, some landings without places:
no stale byte at a tell, title memory never goes back, same end as the old path; without the `Newer` rule a piece
does go back, which the test asserts), `in_flight::tests` (rooms never share a place, out of order; a piece fits its
place; the rule), `tells::tests`, and on the software adapter
`indirect::tests::warp_card_snapshot_copies_what_the_compare_flagged` (behind the real compare, two skews: flagged
pieces get places and their bytes, unflagged none, a room of one gives one place, the counter starts from 0 each
pass, places wrap; it fails if the copied bytes are off by one).

Benchmark (offline, modelled, `cargo test --release -p victory-gpu --lib -- fence_latency_offline --nocapture`):
a made-up frame of 17 flights, ~22 MB in ~340 pieces, the rates from the 7800X3D log (fetch 0.45 ms + 90 us/MB,
merge 370 us/MB, the card copying out 45 us/MB inside the flight); the cuts are the layer's own code. Card done to
told, mean over ~8.7 tells a frame (most): old with 1 part 2.20 ms (5.95), `VICTORY_FETCH_PARTS=4` 1.99 (5.23),
`+ VICTORY_MERGE_SPREAD=1` 1.86 (4.25, -7 %), `+ VICTORY_FETCH_IN_FLIGHT=1` 1.08 (3.56, -46 %), both 1.05 (2.87,
-47 %); the relay landing 19.2 -> 13.0 ms a frame. Cutting a landing of 17 flights costs ~8 us. These are a model;
the game run decides.

Risks: in-flight copies add the copy of the flagged pieces to the card's time inside each flight (~1 ms a frame for
22 MB), and 64 MB of memory the PC reads; a view of title memory reached by two host copies (a heap and a buffer in
it) is ordered per copy only, as before. Spread tells a segment while later segments are merged: a title thread
woken early runs beside the relay's merge (more contention, the reason to measure it).
## Above 768p on Series S: the title's two start-up pools (`VICTORY_TITLE_POOL`, off)

Above a render height of 768 lines the Series S profile stopped within about 6 s of start on an int3 after the
title's out-of-memory handler. Read from the executable (offline): the failing allocator is one of nine pools the
title reserves at start-up from a read-only table of sizes with one row per console, chosen by device type (6 =
Series S). The third pool is write-combined graphics memory (`XMemVirtualAlloc`, protection 0x2404): 1,277 MiB on
Series S, 2,199 MiB on Series X. Nothing in it comes from the title memory the layer reports
(`XMemGetWorkingSetStatistics`); the comment in `console.rs` holds for these pools. With that pool enlarged, 1080p
ran into a second limit: a count of physical 64 KiB pages (`XMemAllocatePhysicalPages`) the title takes at start-up,
an immediate chosen by device type (4,752 pages = 297 MiB; Series X 11,360). At 1080 lines what it maps there needs
432 MiB, and the title checks that against the count with another int3.

New switch, off: **`VICTORY_TITLE_POOL=<factor or MiB>`** (`hooks.rs`, with the render-scale levers). A number up
to 16 is a factor, a larger one the graphics pool's size in MiB (1,277..16,384); the page count grows by the same
factor (at most 65,535 pages: the title shifts it in 32 bits). Two patches, each checked against the build's hash
and the exact bytes first: the Series S row's entry in the size table, and the `mov` of the page count. Series X's
sizes are left alone.

Measured in game (7800X3D / RTX 4070 SUPER, Series S, `measure.ps1` recipe: Enter every 6 s from second 20 to 140,
seconds 150-200 measured, one run each):

| Height | `VICTORY_TITLE_POOL` | Start | fps | 1 % low | hitches > 100 ms | private (MB, end / peak) | gpu_used |
|---|---|---|---|---|---|---|---|
| 768 | off | yes | 24.9 | 13.1 | 0 | 24,259 / 24,880 | 7,898 |
| 810, 900, 960 | 2 | yes (40 s each, no exception) | | | | | |
| 1080 | 2 | yes, into gameplay, 200 s without an exception | 17.2 | 4.8 | 79 | 27,175 / 28,167 | 9,150 |

810 to 1080 crashed before with the switch off. Factor 2 gives 2,554 MiB and 594 MiB. Not measured: the smallest
factor that holds at 1080 (1.5 gives 445 MiB of pages against the 432 needed at start, with no margin for later
scenes), and render heights above 1080, which need an output height above Series S's 1080 first.
## Native mouse aiming (`VICTORY_MOUSE_NATIVE=1`, off by default)

`VICTORY_MOUSE=1` made the mouse the stand-in pad's right stick, so it went through the stick's dead zone, response
curve and acceleration. What the title does with its input, found with the two diagnostics switches below and static
reading of 1.0.2.1 (RVAs of the executable, no code of the title's kept here):

- **Pads.** The per-frame input update (0xa1c260) reads the keyboard (0x43a1c30), then the four pad objects
  (0x7a40f0, each 0x4b0 bytes). A pad's update (0x7a4150) asks our GameInput for the gamepad state (vtable slot
  0xb0), keeps the sticks raw at +0x498 (y negated), applies a radial dead zone (0x1fec90 left, 0x20cd2b0 right, the
  core at 0x1fede0) into +0x38/+0x3c (left) and +0x40/+0x44 (right), and emits a change event per axis
  (0x323a80, sources 0x3010-0x3013, through 0x51e0a00 to the listeners at 0x571d5b0). A pad's source value
  (0x51a4590) maps source 0x3012 to +0x40 and 0x3013 to +0x44.
- **The PC engine's keyboard and mouse device is still there** (vtable at 0x65f2100; "supports" sources of type 0
  keyboard, 0x1000 mouse buttons, 0x2000 mouse axes). Its update (0x5457890) emits key events for every key whose
  state changed (0x43a1890) and, each frame, two mouse axis events (sources 0x2000 and 0x2001, through 0xa75a50) and
  four mouse button/wheel events (0x1008-0x100b). On the console the mouse movement is compiled out: the value is
  `0 * scale` (`vxorps xmm6`, then `vmulss` with two floats in .data at 0xa9e8890/0xa9e8894). Its source value
  function (0x52399b0) answers keys from the keyboard table and 0 for mouse axes.
- **Keyboard.** The keyboard device builds a 256-entry key table each frame (0x43a1c30, from our scan codes and
  virtual keys; readers 0x85eba0 "any key down", 0x43a1610, 0x52399b0 the key/mouse source value, 0x5457890 its
  update). The executable has no key-name strings (only the UI library's `KEY_UP`/`KEY_DOWN`) and no glyph table for
  keys was found.

- **Nothing listens to that device.** Its events go to delegates at device+8 (inlined broadcast in 0xa75a50; key
  events the same way from 0x43a1890). Measured in game (data break at 0xa75b24): with the patch below, 37 mouse
  events were posted in 15 s and the listener list was empty every time; the listener calls (0xa75b3d, 0xa75b79)
  never ran. So the title does not use the keyboard or the mouse for gameplay itself: keys act only through our
  stand-in pad, and button prompts stay the pad's (no key glyph table or key names were found either).

The patch (`crates/victory-loader/src/mouse_look.rs`, measured in game: applied, events posted, **the camera does not
turn from it yet**): the zero becomes the mouse movement. At 0x54578ed the 12 bytes
`vxorps xmm6; vmulss xmm0, xmm6, [scale x]` become a jump to code of ours that takes the counts the input layer
added since the last frame (`xchg`, so none is lost or counted twice), leaves `dx * gain` in xmm0 and `dy * gain` in
xmm6; at 0x545791f `vmulss xmm0, xmm6, [scale y]` becomes `vmovaps xmm0, xmm6`. Both places are checked against
their expected bytes first and the build's hash; any difference changes nothing (a warning, and the mouse stays the
stick). With `VICTORY_MOUSE_NATIVE=1` and `VICTORY_MOUSE=1` the movement goes to the patch and, as before, to the
right stick (without the stick the camera would not turn at all). `VICTORY_MOUSE_NATIVE_SCALE=<x>[/<y>]` sets the value of one
count (0.01 by default; a negative number turns that axis the other way). Diagnostics builds:
`VICTORY_MOUSE_TEST_DELTA=<from>-<to>:<dx>,<dy>` adds that movement every 8 ms in that window (seconds after load).

In game (two runs, prison yard at about 150-200 s): `VICTORY_MOUSE_TEST_DELTA` with 10 and 20 counts per 8 ms for 7 s
(scales 0.01 and 0.05) left the camera where it was in the captured frames; the stand-in stick (`L` held 7 s) turned
it clearly (from the window to the bunk beds) in the same run. Next steps, in order:
1. Find who adds listeners to a pad (data break on writes to pad 0 +0x8, rva 0x9ab1ce8, from the start) and add the
   same listener to the keyboard and mouse device (0x9ab1bc0). If the title's control data has no mouse source for
   looking (likely on the console), that alone does nothing either.
2. Otherwise go past the mapping: follow the right stick's events (0x3012/0x3013) to the listener and from it to the
   camera (`VICTORY_DATA_BREAK=x571d634,x571d5fb` with `VICTORY_DATA_BREAK_SPLIT=rax` while `L` is held lists the
   listeners), find where the look value is scaled by sensitivity and frame time and added to the heading and pitch,
   and add the mouse there (the stub here takes the counts the same way).

Diagnostics switches added for this:
- `VICTORY_INPUT_CALLERS=1`: each chain of title code that reads a pad's or the keyboard's state, logged once.
- `VICTORY_DATA_BREAK=<rva>[:<bytes>]|x<rva>,...` (at most four), `VICTORY_DATA_BREAK_FROM`/`_FOR` (seconds),
  `VICTORY_DATA_BREAK_SPLIT=<register>`: the debug registers of every thread stop on reads and writes of title data
  (or at an instruction); each instruction is logged once with its count, its registers at the first stop and the
  qword at the stack pointer. Hardware data breakpoints set from inside the process work (unit test).

Tests: the scale and test-delta parsing; the site check (synthetic bytes); and the patch run on code of a test's in
the same shape (a zero times a scale, stored twice): it stores the movement times the gains once, takes it, and a
second place that is not the expected bytes leaves both places as they were.

### Fixes (each with a test that fails without its switch)

- **`VICTORY_SIG_ROWS=1`** (`emit/container.rs` `separate_modes`, called from `Shader::finish`). The console's
  compiler packs signature elements into rows its own way, and the modes here are worked out per element. A row
  that ends up with two modes gets its second mode's elements moved to a row of their own past the last one used.
  The code reads and writes elements by number, and D3D12 links stages by semantic, so nothing else changes.
  Test: `a_row_of_two_interpolation_modes_is_split_into_two_rows` (the validator's refusal without it).
- **`VICTORY_LOD_ARRAY=1`** (`image_get_lod` in `lower.rs`). A level query of an array passed the slice as a third
  coordinate; DXIL wants it undefined. Test: `a_level_query_of_an_array_leaves_its_slice_out`.
- With both on, offline: **14,259 of 14,259 vertex and pixel programs validate** (14,215 before); mesh 8,694 of
  8,765 (the 71 above remain).
- **`VICTORY_GATHER_LEVELS=1`**: `image_gather4_l` on a 2D array reads its four texels at the named level and the
  rounded slice (by load, as the 2D case already did); on a cube, four samples at the texel centres at the level
  (a cube view cannot be loaded from; a sample at a texel's centre at a whole level is that texel whatever the
  filter, and texels past the face's edge come from the next face, as the console's gather has them). Before, both
  read level 0. This replaces one of the two "known, kept" errors; nothing is refused. Tests (GPU-run, linear
  sampler, position-coded texels): `a_gather_at_a_named_level_of_a_cube_reads_that_level`,
  `a_gather_at_a_named_level_of_an_array_reads_that_level_and_slice` (each also checks that off reads level 0).
- **`VICTORY_TEXTURE_PARTIAL_EVERY=<frames>`** (30 when unset, as before; `texture.rs`). A texture only some of
  whose pages are mapped (streaming in) is read again at most every that many frames: a level that streams in
  showed up to 30 frames late.

### Diagnostics (log lines only)

- The per-reason drop lines put the skip list's shaders (about 140, 3 a frame each) on one line. They filled the
  40 lines before, so a pipeline the driver refused never showed among them.
- `a view read in its texture's format, not its own` (once per pair of formats, `descriptor/host.rs` `fits`): a

## NVIDIA DLSS through Streamline (`VICTORY_DLSS=1`, off) and the upscaler report (`VICTORY_TAAU_REPORT`)

Steps 1 and 2 of DLSS for the title; the plan for Frame Generation and Reflex is in `docs/dlss.md`.

- **`VICTORY_DLSS=1`** (off; `crates/victory-gpu/src/dlss.rs`). NVIDIA Streamline 2.14.16 (DLSS 310.9) is loaded
  from `%LOCALAPPDATA%\victory\dlss` (or `VICTORY_DLSS_DIR`), only with a valid Authenticode signature, and given
  the host device with manual hooking (`slSetD3DDevice`; nothing goes through Streamline's proxies). The log says
  whether DLSS runs on the card. `scripts\get-dlss.ps1` fetches the files from NVIDIA's public GitHub release
  (SHA-256 checked) into that folder; none of them is in the repository. `VICTORY_DLSS_PRESET=J|K|L|M` picks the
  model. Off: nothing is loaded and no code path changes.
- In the live frame (`draw.rs`, `State::dlss_after`): after the title's pass that `dlss::PASS` names, DLSS Super
  Resolution is recorded from that pass's colour, depth and motion vectors into its output, with the jitter read
  from its constant buffer; the layer then sets its own pipeline, root signature and heaps again.
  The pass is the title's TAA (`TAA2:CS_TAA2_Resolve`), which runs at render size, so DLSS runs there as DLAA
  (960x540 in and out); the title's post-processing and spatial upscale follow. Measured in game: every evaluation
  succeeds after a fix (one frame number per evaluation) and the picture stays whole; quality, the jitter sign and
  the motion scale are not judged yet. Real upscaling needs the title's TAAU pass or DLSS at the spatial upscale
  (`docs/dlss.md`).
- **`VICTORY_TAAU_REPORT=1[,<shader hash>...]`** (diagnostics builds; `taau.rs`): finds the title's upscaler by
  shape (a dispatch that covers the texture it writes, reading two or more textures smaller by one ratio; a
  whole-screen draw reading one) and logs, per binding (root parameter and place in its table), the texture's size
  and format, and the constant buffers' words, six frames in a row and again every 600 (the jitter is the pair that
  moves each frame). Hashes in the list are reported whatever their shape. The 600th sighting captures the next
  frame as F9 does; with `VICTORY_DUMP_TARGETS=1` the pass's textures are dumped, and the dump now logs per channel
  the lowest, highest and mean value and the share of exact 0 and 1 (motion vectors' scale and sign, depth's far
  plane).
- Tests: `dlss::tests::structures_have_streamlines_layout` (every size and offset against Streamline's headers),
  `dlss::tests::gpu_dlss_upscales_a_synthetic_frame` (DLSS Super Resolution on the card, 960x540 to 1920x1080, eight
  jittered frames of two flat halves: largest difference 0.0017 on the RTX 4070 SUPER; skipped without the files or
  an RTX card), `modes_follow_the_scale`, `presets_by_letter`, `result_codes_are_named`; `taau::tests` (the shape
  rule on upscalers, blurs, downsamples, partial dispatches and squashed inputs; the report cadence; reading
  constant words).
- Found on the test PC: Streamline refuses DLSS Frame Generation with "GPU hardware scheduling ... not enabled"
  (`HwSchMode=2` in the registry notwithstanding); Super Resolution and Reflex are supported.

## DLSS upscaling through the title's own TAAU (`VICTORY_OWN_TAAU=1`), proxy swap chain, Reflex markers

- **`VICTORY_OWN_TAAU=1`** (off; `hooks.rs`, with `VICTORY_OWN_UPSCALER=1` and `VICTORY_RENDER_SCALE`): the own
  upscaler's maximum scale is 1 instead of the minimum (eight bytes at `0x28f1e87`, checked). The title then picks
  its temporal upscaler `TAA2U:CS_TAA2_Resolve` each frame (it does so when the render size differs from the
  scene's target size, `0x13f4023`; found by reading the executable and with `VICTORY_DATA_BREAK`) and runs
  post-processing at the output size, instead of TAA at the render size and a spatial upscale of the finished
  picture. Measured in game (540p, one run): `TAA2U` dispatched every frame, `TAA2` never, picture whole,
  26.6-27.3 fps.
- With `VICTORY_DLSS=1` DLSS follows either pass (`dlss::PASSES`): with `VICTORY_OWN_TAAU=1` that is DLSS Super
  Resolution 960x540 to 1920x1080 (Performance), every evaluation succeeding, picture whole (runs C1, D).

### LDS both halves of a console wave read and write in one lane branch (offline)

29 console wave64 compute programs were refused on 32-lane hosts (RTX 4070 SUPER, `VICTORY_HOST_WAVE=32`) with
"LDS in a group over 32" and "an LDS read and write in one lane-branch region". A console wave runs as two host
waves of 32 there. The console runs the wave's 64 lanes in step, so its LDS accesses happen in program order. The
host's two waves keep that order only where they meet at a group barrier, and such a barrier cannot stand in a
block only some lanes run. So a lane-branch region that both reads and writes LDS was refused.

Such a region needs no order when the two halves never touch an LDS dword there in ways that conflict. The new
`emit/lds_apart.rs` proves that per region. It works out every LDS address of the region, and the conditions on
the way to it, for every thread of the group: a constant plus scalars times constants, modulo 2^32. The scalars
are inputs, loads and arithmetic of them, which both halves share. A loop join that adds one constant per round is
its entry value plus the step times a count of rounds; that count is each thread's own and below the loop limit.
Two accesses of the two halves of one console wave then conflict if they may touch one dword, one of them writes,
and they are not the same commuting atomic (`ds_add_u32` and `ds_add_rtn_u32`, `or`, `max` ...). The title's own
barriers in the region split it into parts that are ordered (they wait for the group unless `VICTORY_GROUP_SYNC`
is 0 or 1). Conflicts between threads of different console waves are left alone: the console runs those in no
fixed order either. With atomics the halves may take their slots in another order than the console's lanes
would. Each lane still gets a slot of its own.

It is tried only for programs that no form translated before: `emit` runs all the forms once more with it
(`lower::with_lds_apart`). Every program that translated before keeps its DXIL byte for byte (a whole-game
`translate --list`, host wave 32, same hash for all 25,777 other programs). Applied to every program it would
change 35 that translate today through other forms (`without skips`, the 64-thread reductions of
`compute_graph_ops`, `ambient_map`, `lens_flares` ...), so it is not. `VICTORY_LDS_APART=0` turns the retry off
(in the shader cache's key).

2 of the 29 now translate with host pipelines: `alphaResolve:CS_AlphTransmissionPrefilterMip` (the blurred scene
copy that glass and transmission sample) and `GpuParticleUpdate:CS_Visibility`. The other 27 stay refused:
- 8 where both halves really touch one dword in a region with nothing between (`VICTORY_WAVE_WHY=1` prints
  `WAVE64-LDS-APART ... both halves ... touch`): `sr_tracing:CS_Tiling_Generate_Opaque` (a flag some lanes write
  and the others read in a per-lane loop), the 5 water `CS_TransmissionVolumetrics*` (lane 0 sets up a min/max
  pair that all lanes then update and read), the 2 hair shadow masks;
- 19 whose addresses this does not follow ("an LDS address not known per thread", 2 liquid trails "... that
  differ by a scalar"): the 7 particle emitters
  (records at a slot taken with `ds_add_rtn_u32`, an index modulo a scalar), the 9 decal trail and 3 triangle clip
  programs (slots, lists that lane 63 reads back after the others wrote, bitonic sorts that shift by loop counts,
  bit sets indexed by loaded data).
Tests (`wave64_tests`, run on the card, exact against a CPU model of the console wave): a mip level made in LDS
behind a bounds test with the title's barrier inside it (256 threads, with whole host waves out of bounds);
slots from LDS counters in one console wave with a `64 * s1 + t == 0` region; records walked in rounds of 64 with
an `if`/`else` that reuses the address register. All three were refused before. Still refused: the mip level
without its barrier, a read of the counter the other half adds to, an address a scalar away from the counters, two
kinds of atomics on one dword, and records walked in rounds of 32 (the halves share them).

In game (5dda06b, RTX 4070 SUPER, first start after the build, the scripted route with Enter every 6 s from second
20 to 140, 240 s): both programs got host pipelines; 6 "host pipeline refused" lines against 8 in a run of the same
build with `VICTORY_LDS_APART=0`; no device loss. At the prison cell window (about second 150-160) the window
glass shows the blurred, rippled view of the yard, and the bright fringe around the character's hair against the
window is gone. With the switch off the glass shows a sharp grid with no blur and the hair has that bright fringe.
Frame rates of these first starts were not compared.
